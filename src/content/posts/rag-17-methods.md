## 一句话摘要

RAG 效果的上限由「检索策略」而非「模型或向量库」决定；视频按由浅入深梳理了 17 种检索优化方案，并给出初创探索、企业生产、复杂推理三类场景的推荐组合，最终推荐落地优先级为「Rerank + 混合检索 + 多层次索引」。

## 核心痛点：为什么基础 RAG 总是答非所问

- 常见误区：`RAG = 向量数据库 + 大语言模型`，忽略检索链路设计，导致模型频繁幻觉。
- 真相：相同基座模型下，优秀的检索策略让 AI 化身领域专家，糟糕的策略让 AI 表现为随机抽卡。
- 失效链路：用户提问 → 低效检索（语义断层）→ 大模型理解受阻 → 生成错误回复。
- 根因：单纯堆硬件与模型，无法弥补粗暴检索带来的上下文语义断层。

## 17 种方案总览

| 编号 | 方案 | 一句话原理 | 主要收益 |
| --- | --- | --- | --- |
| 1 | Simple RAG（固定字数硬切） | 按固定字数 / token 切块后向量检索 | 实现最简单，效果最差，是 RAG 的起点 |
| 2 | Semantic Chunking（语义切分） | 按语义断句，话题切换处切块 | 主题统一、逻辑连贯，理解效率提升 |
| 3 | Small-to-Big Retrieval | 小块负责找，大块负责答 | 检索精度 + 上下文完整性兼得 |
| 4 | Context Enriched（上下文增强） | 命中块连同前后邻居一起召回 | 改造成本极低，性价比极高 |
| 5 | Chunk Header（给文本块加标题） | 每个切块附加摘要标题与章节路径 | 碎片块具备全局视野，提升匹配率 |
| 6 | Document Augmentation（文档增强） | 反向生成潜在问题，与原文绑定向量化 | 问题匹配问题，召回率明显提升 |
| 7 | Query Transformation（查询变换） | 改写 / 回退 / 拆解用户提问 | 解决「用户不会提问」导致检索偏移 |
| 8 | Rerank（重排序） | 初筛 Top N 后用重排模型精排 | 投入产出比最高的优化，解决「找得准」 |
| 9 | Sentence Window Retrieval | 命中核心句后向前后滑窗扩展 | 适合法律文书、学术论文、长技术报告 |
| 10 | Context Compression（上下文压缩） | 轻量模型过滤提炼，只留核心内容 | 省 token、降干扰、提升回答质量 |
| 11 | Feedback Loop（反馈闭环） | 采集点赞 / 踩 / 采用率动态调权 | 静态知识库变成长型资产 |
| 12 | Self-RAG（内省反思） | 自问、评估、过滤三步内省 | 该查才查，剔除废料再生成 |
| 13 | Knowledge Graph RAG | 把知识转成实体—关系网络 | 多跳关系推理、跨文档关联 |
| 14 | Hierarchical Index（层次化索引） | 摘要索引 + 分块索引双层结构 | 海量文档下节省算力与响应时延 |

| 16 | Hybrid Search（混合检索） | BM25 关键词 + 稠密向量 + RRF 融合 | 补齐各自短板，几乎必用 |
| 17 | CRAG（Corrective RAG） | 前置质量检查员，三档分流处理 | 检索错也能纠错，动态兜底 |

## 方案详解

### 1. Simple RAG（固定字数硬切）

- 核心思想：把文本按固定长度切块 → 与问题做向量匹配 → 取最相关的几块 → 交给大模型作答。
- 缺陷：硬切分不判断句子是否说完。很多系统的默认规则是每 512 个字符或每 1000 个 token 切一次，导致一句完整的话、一个段落被硬生生切成两半。
- 后果：模型检索到的只有半句话，上下文缺失导致语义不完整，最终回答不准确、逻辑不连贯、容易胡编。
- 结论：实现最简单，效果也最差，但它是理解 RAG 的起点。

### 2. Semantic Chunking（语义切分）

- 核心思想：不看字数死理，而是看语义。两句话讨论同一主题就放一起，话题发生跃迁就切开。
- 动态断句机制：基于句子语义差异判断，当检测到转折词（如「然而」）或话题跳跃时，自动触发边界切分。
- 示例：讲「AI 已在医疗领域广泛应用，AI 正在改变金融行业，然而 AI 的发展也带来了伦理问题」，其中「然而」是明显转折点，系统会在此处自动断开，形成两个切片。
- 收益：主题统一、逻辑连贯，模型理解效率大幅提升。
- 局限：切块仍然偏小，跨段落的信息依然会丢失，只能算第一步优化。

### 3. Small-to-Big Retrieval

- 核心思想：小块找，大块答。
- 做法：将一整章（Parent Chunk）拆成数十个子块（Child Chunk）。检索时比对高灵敏度的子块，最终喂给 LLM 的是完整的父块。
- 类比：去图书馆找资料不会通读整本书，而是先查目录定位章节，再阅读整章内容。
- 收益：小块检索更精准，大块上下文更完整，二者结合。

### 4. Context Enriched（上下文增强）

- 核心思想：命中目标文本块后，检索机制自动向外辐射，把它的前后邻居块一并打包召回。
- 示例：有 1、2、3 三个切块，命中第 2 块时同时返回第 1、3 块。
- 类比：聊天记录里突然看到一句「我不同意」，单看毫无信息量；若补上上下文——「我建议取消会议 / 我不同意 / 因为我下周要出差」，前因后果瞬间清晰。
- 收益：实现成本极低，现有 RAG 系统只需改造检索环节即可升级，效果提升明显，属于性价比极高的改造方案。

### 5. Chunk Header（给文本块加标题）

- 核心思想：在向量化存储前，用小模型为每个切块自动提炼摘要标题，并附带所属章节路径。
- 存储样式：`【章节主旨：AI 医疗应用场景与挑战】+ 正文内容`。
- 类比：读论文先看小标题，理解速度会快很多。标题相当于提前告诉模型这一段的主题是什么，使碎片块天然具备全局视野，大幅提高检索匹配率。
- 注意：不增加文本冗余度，只是让模型更容易理解每块的语义主旨。

### 6. Document Augmentation（文档增强）

- 核心思想：利用「问题匹配问题」的天然优势，不直接单存文档。
- 做法：先对文本块反向生成多条高频潜在问题，将「衍生问题集 + 原文本块」绑定进行向量化。用户提问时可直接与这些衍生问题精准对接。
- 示例：原文「人工智能正在改变现代社会」→ 自动生成「为什么 AI 越来越重要」「AI 如何影响我们的生活」「AI 带来了哪些机遇与挑战」。
- 收益：用户输入本就是问题，问题与问题做互相匹配，天然比问题与段落匹配更容易，召回率明显提升。

### 7. Query Transformation（查询变换）

有时不是文档有问题，而是用户问得有问题。核心思想：在检索之前，先把问题变得更好。用户不会提问，系统来帮忙优化。

- **查询重写**：将模糊的口语提问精细化描述。
  - 原问「AI 依赖大数据有什么问题」，改写为「AI 在处理大规模数据时会遇到哪些挑战，包括数据质量、隐私风险和存储成本的问题」，检索目标变得非常清晰。
- **回退提问**：问题太具体反而不好找答案时，退一步上升到更大的概念背景，先找到相关背景知识再回答原问题。
  - 原问「训练一个 AI 模型需要多少数据」→ 先变成「数据驱动的 AI 系统面临哪些挑战」。
- **子问题拆解**：复杂大长句拆解成多路并行检索，最后汇总。
  - 原问「AI 对医疗行业有哪些影响」→ 拆成「AI 如何辅助医生诊断」「AI 如何提升医疗效率」「AI 是否会改变医生工作流程」，分别检索后汇总答案。
- 优势：特别适合模糊问题、复杂问题、多条件问题。

### 8. Rerank（企业落地高产出比策略）

- 定位：前面的方案解决「找得到」，Rerank 解决「找得准」。
- 问题：向量检索往往只管「长得像不像」（海选），看起来都很像，实际根本没用。
  - 例如问「苹果手机多少钱」，返回结果里 A 讲 iPhone 售价、B 讲苹果是一种水果、C 讲苹果公司要发新品——向量检索觉得三个都含「苹果」，但人一眼就知道 A 才是答案。
- 做法：先用向量检索得到候选集（初筛 Top 50），再由重排模型对候选逐条精细打分（决赛），精选 Top 5 送入大模型。
- 类比：向量检索像海选，Rerank 像评委。海选过得去就能进候选，决赛得有真实力。
- 结论：投入产出比最高的 RAG 优化方案，很多企业做 RAG 优化的第一件事就是在检索候选环节加 Rerank。

### 9. Sentence Window Retrieval

- 问题：答案可能并不存在于单个切片里，而是分散在连续几个切片中。
- 示例：一篇论文分为「实验背景｜实验设计｜实验结果｜实验结论」，如果只返回「实验结论」这一块，缺少前面的实验过程，答案就不完整。
- 做法：命中高分切片后，自动向前后延伸扩展「滑窗机制」，将连续内容一起召回后整体交给模型。
- 类比：看电视剧只看到大结局，根本不知道前面发生了什么；连续看几集才能明白剧情走向。
- 适用：法律文书、学术论文、长篇技术报告等高度依赖上下文推理的场景。

### 10. Context Compression（上下文压缩）

- 问题：检索回来的内容太多。例如问「特朗普为什么比拜登强」，却召回 5000 字论文，而真正回答问题的只有 200 字。
- 做法：召回长篇幅段落后，用轻量模型先过滤与提炼，萃取真正核心的 200 字重点再喂给主模型。
- 流程：检索 → 压缩 → 保留关键内容 → 生成答案。
- 类比：考试时老师给你一本 300 页教材，你要的不是原书，而是一本划好重点的参考书。
- 收益：节省 token、减少干扰、提升回答准确率。

### 11. Feedback Loop（反馈闭环）

- 核心思想：引入类似搜索引擎的学习进化能力，让静态知识库变身成长型资产。
- 流程：用户提问 → 系统回答 → 用户反馈（点赞 / 踩 / 采用率等显隐性行为）→ 记录反馈 → 优化排序。
- 示例：某文档权重为 0.8，用户持续点赞其答案，系统将其权重提升到 0.9 或更高，之后类似问题优先返回该文档。
- 类比：刷抖音点赞会强化推荐。为什么重要？因为 RAG 原本是静态知识库，反馈闭环让它变成会成长的知识库。

### 12. Self-RAG（内省反思机制）

- 起点问题：是不是所有问题都需要检索？例如「太阳绕地球一圈需要多久」这种常识，模型本来就知道，没必要查库。
- 做法：赋予大模型三步内省能力。
  1. **自问**：我自身已具备该常识吗？（不盲目查库）
  2. **评估**：检索回来的资料真的能切中要害吗？
  3. **过滤**：剔除废料，仅用高质量知识生成回答。
- 流程：用户提问 → 模型自我判断 → 是否需要检索 → 检索结果评估 → 生成回答。
- 类比：考试时简单题直接写，难题才打草稿。

### 13. Knowledge Graph RAG

- 定位：企业级高级方案。前面所有技术处理的都是「文本」，但现实世界很多知识不是按文本组织，而是按「关系」组织的。
- 问题示例：问「孙悟空是谁的徒弟」，普通 RAG 能回答「拜菩提祖师为师」；但继续问「孙悟空的师父还有其他徒弟吗」「唐三藏和菩提祖师是什么关系」，普通 RAG 就答不出来，因为答案分散在多篇文章块里。
- 做法：将知识转化为「节点 + 关系」的确定性网络（孙悟空 —师父→ 菩提祖师；唐三藏 —徒弟→ 孙悟空；猪八戒 —师兄弟→ 孙悟空）。查询时不再全文搜索，而是在图谱里直接查关系，类似查地图导航而非翻百科全书。
- 优势：长链推理（A 连 B、B 连 C、C 连 D，问 A 与 D 的关系）与跨文档关联天然胜任。普通 RAG 很难把散落在文档 1、2、3 里的 A、B、C 串起来。
- 代价：构建成本高，需要实体识别、关系抽取、图谱校验。
- 适用：医疗、金融、法律等知识密集型高价值场景。

### 14. Hierarchical Index（层次化索引）

- 定位：面向百万级海量文档的双层架构，可称为知识库中最经典的结构。
- 问题：公司有 100 万份文档，用户问「公司报销制度是什么」，不可能全库扫描。
- 做法：构建 `Summary Index + Chunk Index` 双层框架。
  1. 先比对大纲 / 目录层级索引，锁定极小局部范围；
  2. 再深入具体精细切块展开微观检索。
- 示例：一本书第一章讲 AI 基础、第二章讲深度学习、第三章讲 Transformer。用户问「Transformer 为什么效果这么好」，系统先定位第三章，再只在第三章内搜索。
- 类比：去图书馆找科技类书籍，先看类目、再找书架、最后找到具体书目。
- 收益：大范围收小检索范围，减少无关干扰，大幅节省算力与响应时延。

### 15. HyDE（假设性文档嵌入）

- 核心思想：先猜答案，再凭证据按图索骥。
- 问题：用户提问与文档内容表达方式完全不同。例如用户问「如何预防感冒」，而文档写的是「保持良好的作息规律、提高免疫力」——「感冒」这个词根本没在文档里出现，传统向量检索可能找不到。
- 做法：先让大模型凭空盲猜生成一份理想中的「虚拟答案」（如「预防感冒的方法包括保持充足睡眠、均衡饮食、加强锻炼、勤洗手」），再用这份语义丰满的假答案去匹配向量库中的真证据。
- 有效原因：用户问题往往很短，而假设性答案已经生成了一段完整语义，更容易匹配到真实文档。
- 缺陷：如果模型一开始就猜错了，后续会全部跑偏。例如问 AI 医疗应用，模型误以为是「机器人手术」，就会遗漏真正重要的相关信息。
- 结论：效果不错但不稳定，通常需要与其他方案搭配使用。

### 16. Hybrid Search（混合检索）

- 问题：向量检索和关键词检索各有缺陷。向量检索靠语义相似，可能把语义空间接近但并非答案的内容召回；关键词检索则缺乏上下文语义理解。
- 做法：企业级硬通货，两套底层引擎同时并发启动。
  - **第一路**：传统 BM25 关键词检索（抓死特定型号、代码、专有名词）。例如用户问 GPT5，就必须精确命中「GPT5」这个词。
  - **第二路**：稠密向量检索（理解意图与相近语义）。例如问「如何避免感冒」，即使文档写「增强免疫力」也能语义关联。
  - **最后**：执行 RRF 融合，把两路结果做排名与分数合并，完美互补各自短板。
- 收益：几乎必须采用的方案，基本解决了漏召问题。在法律、医疗、金融这类「宁可多查也不能漏查」的场景非常合适。

### 17. CRAG（Corrective RAG）

- 问题：普通 RAG 的检索结果质量不稳定，有时很好，有时召回一堆垃圾，而系统并不知道，还硬着头皮生成，于是产生幻觉。
- 做法：设置前置「质量检查员」，对检索回来的文档矩阵自动划分为三条演进路线。
  - **高相关（绿灯）**：直接进行传统 LLM 生成。
  - **中相关（黄灯）**：引入外部网络搜索，强力补充细枝末节。
  - **低相关（红灯）**：彻底废弃垃圾检索物，由全量互联网检索全权托管。
- 流程：用户提问 → 检索 → 评估检索质量 → 决定下一步 → 生成回答。
- 类比：写论文时资料特别靠谱就直接引用；资料有点问题就继续查相关文献；资料全是营销号就直接丢掉。
- 价值：解决 RAG 最核心的「检索错、回答也错」问题——检索错了会先纠错再回答。

## 落地决策：面对真实场景，企业该如何选型

根据项目所处阶段与业务严苛程度，进行科学的技术栈积木式组合。

| 应用场景阶段 | 推荐工程组合 | 核心收益特点 |
| --- | --- | --- |
| 初创项目 / 敏捷探索 | Simple RAG + Semantic Chunking + Rerank | 极低改造成本，迅速扫清 80% 常见检索漏洞 |

UP 主的个人选择：**Rerank + 混合检索 + 多层次索引**。理由是目前大多数优秀 RAG 系统的背后，几乎都采用了这几项技术方案。

## 可复用要点

1. 决定 RAG 效果的是检索策略，不是模型大小和向量库品牌——同样的基座模型，检索设计差距就是「领域专家」与「随机抽卡」的差距。
2. 分块策略是第一性因素：硬切分是万恶之源，语义切分只是及格线，Small-to-Big / 上下文增强 / 窗口检索都是在补「上下文完整性」这块短板。
3. 检索侧的两个正交方向：解决「找得到」（Query Transformation、文档增强、HyDE）与解决「找得准」（Rerank、混合检索）。
4. Rerank 是性价比最高的单点优化，企业做 RAG 优化的第一件事通常就是加 Rerank。
5. 混合检索（BM25 + 向量 + RRF 融合）几乎是生产环境必选项，专治漏召，尤其适合法律、医疗、金融等不能漏查的场景。
6. 上下文压缩、上下文增强这类改造，实现成本低但收益明显，适合作为快速见效的工程手段。
7. 高级方案（知识图谱、Self-RAG、CRAG）解决的是长链推理与动态兜底，代价是构建与运维成本高，需按业务价值决定是否投入。
8. 不要把所有问题都交给检索：Self-RAG 的「自问」提醒我们，模型已知的常识无需查库。

- 课件中的「Top 50 → Rerank → Top 5」等具体参数是示例值还是经过实验验证的推荐值，需结合自身数据调优。
